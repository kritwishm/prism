01 · OVERVIEW

What it is, in five sentences.

Prism is a CLI pipeline that turns a single company URL into structured intelligence and personalized landing-page copy. The scraper fetches and cleans the company's website via Jina Reader; three Claude agents then run in sequence to extract facts, classify the account along five ICP factors, and write page-ready copy. A deterministic Python function turns the classifications into a 0–100 ICP score and a tier. The result is written as a structured document to Sanity (the CMS) and upserted as a Company record in HubSpot (the CRM) with custom properties an AE can scan in a single glance.

The two systems are cross-linked: HubSpot holds the scoring summary an account owner needs daily; Sanity holds the rich, editable analysis and copy that drive the personalized page. A local JSON dump captures the full payload for replay and audit.

02 · PIPELINE

Five stages, each with one job.

Sequential by design. Each LLM stage uses Claude's structured-output mode - the model can only return JSON matching the schema we hand it. Python then type-checks the response before it moves forward. If validation fails, we retry once with the error fed back into the prompt.

03 · SCORING

The LLM classifies. Python scores.

The model never emits points. It picks one enum value per factor and provides evidence. A pure Python function in prism/scoring.py maps each classification to its point value and sums to 100. Auditable. Reproducible. Tunable. Testable.

PROPERTY 01

Auditable

The formula lives in one file. No prompt-spelunking required to know how a score was produced.

PROPERTY 02

Reproducible

Same signals → same score, every run. Zero LLM variance on the math itself.

PROPERTY 03

Tunable

Reweight a factor by editing a constant. No prompt change, no re-eval of every historical record.

PROPERTY 04

Testable

score_company(synthetic_signals) == expected_total is a real unit test.

PROPERTY 05

A/B-able

Ship SCORING_VERSION v2.0, route a cohort, measure which formula better predicts win rate.

PROPERTY 06

Evaluable

Signal-extraction quality and scoring-formula correctness become independent evals.

The formula

  ICP_SCORE  =  INDUSTRY_POINTS[ industry.category ]              (max 30)
             +  SCALE_POINTS  [ scale.member_count_band ]
                  + ENTERPRISE_BONUS   if has_enterprise_customers
                  + NAMED_BONUS        if has_named_customers
                  capped at 25                                  (max 25)
             +  NETWORK_POINTS[ provider_network.network_type ]  (max 25)
             +  GROWTH_POINTS [ growth.stage ]                   (max 10)
             +  READINESS_POINTS[ buying_readiness.level ]       (max 10)
             ────────────────────────────────────────────────────
             =  total                                           (0–100)

The render floor - when the system doesn't commit to a page

Every analyzed company - A, B, C, D - lands in Sanity. Sanity is the analysis-of-record. What changes is whether the system generates copy and whether the doc renders as a public page.

The threshold is an ICP score of 50. Below it:

  • The copywriter agent doesn't run - no hero, no pain paragraph, no CTAs.
  • The Sanity doc still exists, with facts + signals + breakdown + reasoning. Copy fields are empty.
  • The Next.js renderer 404s the public URL - the doc isn't published as a page.

Why this split: Sanity is the analyst-facing surface (full reasoning, override-able, audit-able). The /p/{slug} route is the prospect-facing surface (only renders things worth showing). One store, two policies.

Score ≥ 50 (Tier A, B, high-C)

✓ Extractor agent
✓ Classifier agent
✓ Copywriter agent
✓ Sanity doc (facts + signals + copy)
✓ HubSpot record
✓ Renders at /p/{slug}

Score < 50 (Tier D, low-C)

✓ Extractor agent
✓ Classifier agent
✗ Copywriter - skipped
✓ Sanity doc (facts + signals, no copy)
✓ HubSpot record
✗ /p/{slug} returns 404

Why keep sub-floor docs in Sanity at all? Because the analysis itself is valuable for AEs reviewing rejections, for marketers spot-checking the system's calls, and for the override flow when someone wants to manually push a D to publishable. The render floor decides what's public, not what's stored.

Intent themes & pain points - what they're for

The classifier returns two enriched lists alongside the 5 factor classifications: intent themes (3–6 areas of inferred buyer interest) and pain points (2–5 problems with evidence quoted from the source content). Each item carries its own 0–100 confidence.

Critical anchoring rule baked into the prompt: these MUST be about CertifyOS's product space - credentialing, licensing, provider enrollment, network management, provider data infrastructure. Not the prospect's own marketing themes. Not the pains the prospect solves for their customers.

✓ Correct intent theme

"Multi-state provider licensing automation"
"Credentialing for a growing therapist network"
"Network adequacy reporting for CMS compliance"

These are things the prospect might buy from CertifyOS.

✗ Wrong intent theme

"Patient intake automation" ← Phreesia's product
"Consumer prescription savings" ← GoodRx's product
"Meditation and wellness" ← Calm's product

These are the prospect's own marketing themes - useless to the CertifyOS AE.

When a prospect has no plausible CertifyOS-relevant intent or pain (industry = NOT_HEALTHCARE, network_type = NONE/TANGENTIAL), the classifier is instructed to return empty arrays. Empty is correct. Fabricating themes for a consumer brand is worse than silence - it pollutes the AE's signal.

Tier mapping

RangeTierMeaning
90–100TIER AElite fit - health plan with 100K+ lives, or digital health where the provider network is the core asset.
70–89TIER BStrong fit, likely buyer with one weaker dimension.
40–69TIER CAdjacent - could use credentialing data but it's not the core problem.
0–39TIER DMisfit - not healthcare, or healthcare without provider needs.

Confidence model

Two layers, deliberately distinct:

data_confidence

how complete is the scrape?

Three buckets - high / medium / low - driven by how many pages came back substantive. Propagates through every stage and lands on the HubSpot record so AEs see it.

score_confidence

how sure are we of the number itself?

Continuous 0–100. Computed as a weighted average of the five signal-level confidences (weights mirror the factor caps). A high score with low confidence is a "look closer" flag, not a green light.

05 · ARCHITECTURE

One module, one job.

Each module is ≤200 lines. Names tell you what they own. Boundaries are enforced by what each module is allowed to import.

prism/config.py

Config

Env loading, constants, fail-fast validation on import.

prism/models.py

Models

Pydantic schemas - single source of truth. ICPSignals, ICPAnalysis, ScoreBreakdown, CopyBlocks all live here.

prism/scraper.py

Scraper

Jina Reader wrapper. Three-layer URL discovery: sitemap.xml → homepage links → keyword fallback. Page role tagging.

prism/agents.py

Agents

Three Claude calls - extractor, classifier, copywriter. Tool-use mode + Pydantic validation + one-shot retry on validation error.

prism/scoring.py

Scoring

Deterministic 5-factor scoring. Pure Python functions, no LLM calls. SCORING_VERSION stamped on every record.

prism/sanity_client.py

Sanity client

Content Lake HTTP API. createOrReplace on the analysis doc, patch for the HubSpot backlink.

prism/hubspot_client.py

HubSpot client

Search-by-domain → upsert. Standard industry field is skipped (HubSpot enum mismatch); the analysis lives in 10 custom prism_* properties.

prism/pipeline.py

Pipeline

Wiring across stages. Optional --dump writes a complete per-run JSON to examples/runs/.

06 · DECISIONS

Why · why · why.

Every visible decision in this build, with the thing that was deliberately not chosen.

Choice
Why
Rejected
Jina Reader for scraping
JS rendering + content cleaning in one call. Saves ~60 min vs Playwright on the demo and lets that time go into the analysis layer where differentiation lives.
Playwright fallback chain - over-engineered for a POC, ~85% of sites are fine with Jina.
Three Claude calls
Each agent has one job. Outputs are inspectable, individually evaluable, and at scale individually swappable to cheaper models.
One mega-prompt - mixes concerns; agent-orchestration framework - opacity without value at three steps.
Tool-use + Pydantic
Schema is enforced at the API layer; the response is validated into a typed class on receipt; one-shot retry-with-error feedback on validation failure.
Free-form JSON parsing - fragile and unrecoverable on a typo.
Deterministic Python scoring
Auditable, reproducible, tunable, testable, A/B-able. Signal extraction quality and formula correctness become independent evals.
LLM-emitted scores - opaque, drifty, no clean way to A/B-test the formula.
Layered URL discovery
Real sites use /our-story, /why, /about-oncohealth. A hardcoded list misses non-standard layouts.
Static path list alone - fails the "non-standard layouts" requirement.
HubSpot properties (not custom objects)
AEs work on the company record. Properties show in standard views and reports.
Custom objects - heavier to set up, harder for AEs to find.
Python (for now)
Fastest path to a working pipeline. LLM tooling is Python-native.
TypeScript end-to-end would unify Sanity + Next.js with the pipeline; right move at v2.
07 · DATA MODEL

Three stores, one analysis.

Same data, three shapes - each tuned to who reads it.

STORE 01 · SANITY

Analysis-of-record

Who reads it: marketers (in Sanity Studio), AEs reviewing rejections, the Next.js page renderer.

Shape: one companyAnalysis document per company - every analyzed account, all tiers. _id = companyAnalysis.<slug>, upsert via createOrReplace.

Contains: facts, full ICP analysis (score, tier, breakdown, signals), missing-data list, scoring version. Copy blocks present only when score ≥ 50.

Studio surfaces: tier folders, plus dedicated "Public pages" (score ≥ 50) and "Below threshold" (score < 50) views.

STORE 02 · HUBSPOT

AE-facing summary

Who reads it: account owners, in their daily workflow.

Shape: Company record keyed by domain. Every analyzed account lands here - A, B, C, and D. Standard industry field is skipped. 10 custom prism_* properties.

Contains: the score, the tier, the reasoning, intent themes with confidences, plus prism_sanity_url linking to the full analysis in Sanity (every record has one now, since every analysis is in Sanity).

STORE 03 · LOCAL JSON

Audit + replay

Who reads it: the developer, reviewers, evals.

Shape: one file per run at examples/runs/<slug>.json. Written when --dump is passed.

Contains: everything - summary, scrape, facts, icp, copy. Use to share results without API access.

The Sanity Studio (marketer surface)

The schema is shaped to make the Studio usable by a marketer, not a developer. Four design choices:

01 · TIER-BASED DESK

Sidebar grouped by ICP tier

Custom structureTool exposes "By ICP Tier" folders - 🟢 A, 🟡 B, 🟣 C, 🔴 D - each pre-filtered and sorted by score desc. A marketer can ignore D-tier entirely and focus only on accounts worth personalizing.

02 · FIELD GROUPS (TABS)

Document split into 5 tabs

Identity · ICP Scoring · Intent & Pain · Page Content · Metadata. A long document becomes navigable. The marketer lives in Page Content; everything else is reference.

03 · READ-ONLY MACHINE OUTPUT

Marketers can only edit copy

Score, tier, breakdown, signals, metadata are all readOnly: true. Only heroHeadline, subheadline, valueProp, painParagraph, and CTAs are editable - exactly the surface a marketer should touch.

04 · RICH LIST PREVIEW

Every row shows tier + score + confidence

The sidebar entry for each company displays a colored dot, tier letter, score/100, confidence%, and data-confidence flag at a glance. No need to open the doc to triage.

08 · FAILURE

What breaks first under load.

Three failure modes in the order they bite. Each one already has a partial mitigation in the code; full hardening is the v2 work.

↑ MOST LIKELY · #1

Prompt drift on Claude version bumps

A model update introduces newly-verbose responses or shifts a tool-input field type. The pipeline silently parses fewer fields. Mitigation: eval harness in CI on every prompt change; pinned model versions; the retry-with-error-feedback in agents._call_claude_structured.
#2

HubSpot search rate limits

The _find_company_by_domain search call is the first endpoint to throttle on a batch run. Mitigation: semaphore + exponential backoff; pre-load existing domains at batch start; the search is already wrapped in a broad exception handler that degrades to "no match" rather than crash.
#3

Jina rate limits + aggressive anti-bot sites

Free Jina tier rate-limits at ~20 RPM. Some sites Jina cannot crack (Cloudflare-protected, login walls). Mitigation: confidence-flag downgrade propagates to HubSpot; pipeline aborts before any LLM call if 0 pages succeed; self-hosted Browserless covers the long tail at scale.

Three layers of degradation in the scraper

   per-page failure  ──▶  one 403 doesn't kill the run
        │
        ▼
   confidence flag   ──▶  high (≥3 pages) / medium (1–2) / low (0)
        │                 propagates ALL the way to HubSpot AE view
        ▼
   hard abort        ──▶  0 pages → return before LLM call
                          (no slop generation on blocked sites)

SHIP-IT-FIRST · Parallelize Jina

The cheapest single-shot win

Today the scraper fetches 10 candidate URLs serially. On a slow site (OncoHealth's worst page took 26 seconds), the scraper alone burns ~2 minutes per company. asyncio.gather on the per-URL fetch shrinks that to the slowest single page (~25s instead of ~135s).

Tradeoff: a single batch of 10 concurrent calls can hit Jina's free-tier rate limit (~20 RPM) faster than the serial version. Mitigation: a semaphore in the scraper limiting concurrency to ~5 per host, plus exponential backoff on 429s. ~30 lines of change in prism/scraper.py, no architectural shift.

Why this lands first at v2: biggest wall-time win across every demo and every batch run. The agent stages are already fast (~50s combined); the scraper is the bottleneck.

SOURCE · GONG

Transcript-derived intent

Highest signal-to-effort ratio. Run a classifier pass on Gong call transcripts for competitor mentions, stated pains, timelines, decision criteria.

"Credentialing pain mentioned 3× on a call" beats 50 website scrapes.
SOURCE · SALESFORCE

Behavioral lift

Email opens, clicks, meeting density, contact role spread, opp-stage transitions. Behavior, not intent - adds a behavioral component on top of the ICP score.

Result: quiet Tier A often loses to engaged Tier B.

Build order: Gong first. The classifier model already has a structured-extraction shape; pointing it at transcripts is a small change. SFDC behavioral signals are mechanical aggregations on top.

12 · MEASUREMENT

Four layers. The bottom one matters.

LAYER 01

System health

Scrape success rate · LLM parse success rate · write success rate · latency p50/p95 · cost per company. Fix these before measuring anything else; cost per company is what catches regressions before the bill does.

LAYER 02

Content quality (proxy)

5% sample for manual review against an anti-fluff rubric. LLM-as-judge to scale. Track the trend across prompt changes - never measure a prompt diff in isolation.

LAYER 03

Pipeline impact (causal)

Holdout A/B. Inbound - 50% personalized vs 50% generic, measure demo-book conversion. Outbound - prism copy vs templated, measure reply rate and meeting rate. Holdout is non-negotiable.

LAYER 04 · THE ONLY ONE

Revenue

Closed-won attributable to prism-analyzed accounts vs not. 90-day rolling win rate by ICP tier - does the scorer actually predict win rate? If A doesn't beat C, the classifier is decorative and should be ripped out.

"Are AEs opening the Sanity doc before their first call?" That's the gut metric.

High open rate + better win rate → the system works. Ignored → it's producing slop dressed up as intelligence, and that's worse than no system at all.
